## Problem Statement

`bff-pipeline-v2` — runner, который ведёт AI-агента по этапам 0–6 (preflight, schema, datasource, resolver, e2e, client-codegen, apollo) и отдаёт детерминированный PASS/FAIL/BLOCKED.

Сегодня концепт «этап» не существует как модуль. Знание о каждом этапе размазано минимум по четырём местам, которые обязаны совпадать вручную:

1. CLI-вход содержит if/else-цепочку по номерам этапов 0–6 для команды `verify`.
2. Оркестратор (команда `run`) содержит **дословный дубль** той же цепочки.
3. Модуль fingerprint содержит ещё две if-цепочки: какие поля manifest попадают в хэш и какие файлы хэшировать для каждого этапа; ради этого он импортирует семь модулей чужих этапов и «знает устройство всех».
4. Валидация manifest знает, какие поля обязательны для каждого этапа.

Дополнительно этапы говорят на разных языках: gates этапов 0–3 возвращают просто список checks, а этапы 4–6 — `{ checks, e2eMeta | clientMeta | apolloMeta }`, и оба потребителя (CLI и оркестратор) распаковывают эти именованные поля — шов широкий и продублированный.

Цена: добавление этапа 7 или изменение входа существующего этапа требует согласованных правок в 4–5 файлах. Ошибка рассогласования (например, поле забыли в срезе manifest для fingerprint, а gate его использует) живёт именно в шве между модулями и всплывает только в рантайме.

## Solution

Каждый этап становится самостоятельным модулем-«паспортом»: один файл, в котором собрано всё знание про этап — обязательные поля manifest, входы fingerprint, запуск gate. Реестр этапов — явный список таких паспортов. CLI, оркестратор, fingerprint и валидация manifest перестают знать про конкретные этапы: они спрашивают у реестра «дай этап N» и работают с любым этапом одинаково.

На границе реестра все этапы говорят на одном языке: `run` возвращает `{ checks, meta }`. Потребители больше не называют поля `e2eMeta`/`clientMeta`/`apolloMeta` по имени — нормализация происходит внутри паспорта соответствующего этапа.

Добавление нового этапа после реализации: создать файл-паспорт + одна строка (import) в явном списке реестра. Никакие другие модули не трогаются.

## User Stories

1. As a разработчик, добавляющий этап 7, I want создать один файл-паспорт и добавить одну строку в реестр, so that я не правлю CLI, оркестратор, fingerprint и валидацию manifest вручную.
2. As a разработчик, I want увидеть полный набор этапов одним взглядом на явный список, so that не гадаю, откуда этап берётся (без авто-discovery магии).
3. As a разработчик, читающий чужой этап, I want открыть один файл и увидеть всё про этап: поля manifest, файлы для хэша, запуск gate, so that не собираю картину по четырём модулям.
4. As a AI-агент, вызывающий `verify --stage N`, I want тот же внешний JSON-контракт (`status`, `compact`, `logPath`, `checks` только при проблемах), so that мои интеграции не ломаются.
5. As a AI-агент, вызывающий `run`, I want resume по fingerprint работать как раньше, so that прогоны не инвалидируются из-за рефакторинга.
6. As a мейнтейнер runner, I want CLI и оркестратор без if-цепочек по номерам этапов, so that диспетчеризация существует в одном месте — в реестре.
7. As a мейнтейнер runner, I want fingerprint-модуль, который не импортирует модули этапов, so that он не ломается при добавлении этапа.
8. As a мейнтейнер runner, I want тексты ошибок валидации manifest без изменений, so that существующие тесты и привычные сообщения сохраняются.
9. As a мейнтейнер runner, I want кумулятивную валидацию manifest (поля этапов ≤ N) как раньше, so that поведение `verify --stage N` не меняется.
10. As a потребитель результата gate (CLI, оркестратор), I want единый `{ checks, meta }` от любого этапа, so that я не распаковываю `e2eMeta`/`clientMeta`/`apolloMeta` по именам.
11. As a автор будущего этапа, I want `meta.compactMeta` внутри единого meta, so that компактная строка результата собирается без знания устройства этапа.
12. As a разработчик, I want запуск полного набора тестов без правок существующих тестов, so that рефакторинг доказан отсутствием изменений поведения, а не переписыванием тестов.
13. As a мейнтейнер, I want контрактный тест реестра (обязательные поля паспорта, порядок этапов 0–6, ошибка на неизвестный этап), so that битый паспорт ловится тестом, а не рантаймом.
14. As a разработчик, I want отсутствие новых зависимостей, so that runner остаётся самодостаточным (решение #26 CONTEXT.md).
15. As a AI-агент, I want команды `preflight check/apply` работать как раньше, so that этап 0 не меняет своего внешнего поведения (apply остаётся отдельной командой, не gate).
16. As a мейнтейнер, I want `STAGE_COUNT` в одном месте (реестр), so that границы цикла и валидация `--from-stage` читают одно истинное число.
17. As a ревьюер, I want diff, где удалено больше строк, чем добавлено в модулях-диспетчерах, so that видно, что это углубление модулей, а не перестановка кода.
18. As a разработчик, I want паспорт этапа как единственное место, знающее про `e2eMeta` своего gate, so that знание про устройство этапа имеет одного владельца.

## Implementation Decisions

- **Новый модуль — реестр этапов** (`stages/`): явный список паспортов `STAGES` (порядок = номера этапов), `getStage(id)` с ошибкой на неизвестный id, `STAGE_COUNT = STAGES.length`. Выбран явный список, а не авто-discovery по папке: видимость и простые тесты важнее экономии одной строки (решение подтверждено на grilling).
- **Паспорт этапа** — объект-дескриптор. Shape (из прототипа-плана, кодирует решение точнее прозы):

  ```js
  {
    id: 2,
    name: 'datasource',
    validateManifest(manifest) { /* throws, тексты ошибок дословно как сейчас */ },
    manifestSlice(manifest) { /* поля для хэша */ },
    files(config, manifest) { /* абсолютные пути для fileDigest */ },
    extraParts(config, manifest) { /* не-файловые части хэша, напр. api-schema pin */ },
    async run(config, manifest, ctx) { /* → { checks, meta } */ },
  }
  ```

  `validateManifest` и `extraParts` опциональны (этап 3 не имеет своих полей, этап 0 не имеет extraParts).
- **fingerprint-модуль** становится тонким: умеет хэшировать части, но не знает, откуда они берутся — `manifestSlice`, `files`, `extraParts` приходят из паспорта. Семь импортов модулей этапов удаляются. Состав и порядок частей хэша **не меняются** — существующие fingerprint продолжают совпадать, resume не инвалидируется.
- **Валидация manifest**: `STAGE*_FIELDS` и все проверки формата (HTTP-методы, assertions, expectedTypes, apolloKind) переезжают в паспорта **дословно**. Публичная функция `validateManifestForStage(manifest, stage)` остаётся фасадом: базовая валидация + паспорта этапов ≤ N (кумулятивность сохраняется). Сигнатура и тексты ошибок не меняются.
- **Единый контракт на границе реестра**: `run` любого паспорта возвращает `{ checks, meta }`, причём `meta` включает `stack`, `operation` и опционально `compactMeta`. Сигнатуры самих gates **не меняются** (осознанное упрощение): паспорт этапа — единственное место, которое знает про `e2eMeta`/`clientMeta`/`apolloMeta` своего gate и нормализует их в `meta`. Это удаляет дубли распаковки из CLI и оркестратора, не трогая ~73 вызова gates в тестах.
- **CLI**: if-цепочка диспетчеризации этапов удаляется; `verify --stage N` = `getStage(N).run(...)` + общий хвост (лог, fingerprint, state, print). Команда `preflight apply` остаётся отдельной — apply не является gate. `verify --stage 0` сохраняет текущее поведение (псевдо-manifest `{ stack }`, без валидации manifest).
- **Оркестратор**: `defaultRunStage` (~75 строк if-цепочки) удаляется; цикл вызывает `getStage(stage).run(...)`. Логика reuse/override/state не меняется.
- **Общий базовый кусок паспортов** (базовые поля manifest для хэша) — один маленький shared-модуль внутри `stages/`, чтобы не копипастить его семь раз. Циклических импортов нет: shared ← паспорта ← index ← fingerprint/manifest/orchestrator/CLI.
- **Без новых зависимостей** — только `node:*` (решение #26 CONTEXT.md).
- Волна 2 (адаптер «exec → check», удаление дублей `runTypeCheck`/`allPassed`) — **отдельной** задачей после зелёной волны 1 (решение на grilling: идти двумя волнами).

## Testing Decisions

- Хороший тест проверяет внешнее поведение, а не детали реализации: статусы PASS/FAIL/BLOCKED, тексты ошибок, JSON-контракт CLI, resume по fingerprint.
- **Существующие швы сохраняются и являются главным доказательством**: gate-тесты зовут `run*Gate` с подменённым `exec` (fixture-стиль, node:test) — не трогаем; тесты оркестратора подменяют `runStage` — не трогаем. Все 146 существующих тестов должны остаться зелёными **без правок** — это критерий «поведение не изменилось».
- **Новый шов — ровно один**: контрактный тест реестра. Проверяет: у каждого паспорта есть обязательные поля (`id`, `name`, `manifestSlice`, `files`, `run`), `id` идут 0..6 по порядку без дыр, `getStage(unknown)` бросает понятную ошибку, `run` каждого паспорта возвращает `{ checks, meta }` (на моках). Prior art — fixture-тесты в `tests/*.test.mjs` с табличным репортером; новый файл добавляется туда же, репортер дополняется одной строкой label/intro.
- **Smoke-проверка после реализации**: `preflight check --stack bff-admin --json` на живом workspace + полный прогон `test`.
- Тестовый дубль сигнатур: поскольку сигнатуры gates не меняются, правок gate-тестов не требуется; если в ходе реализации обнаружится скрытая зависимость теста от внутренностей fingerprint/manifest — тест чинится минимально, с записью в «Further Notes» MR.

## Out of Scope

- Волна 2: адаптер «exec → check» (commandCheck), перенос `allPassed` в модуль результата, удаление ~5 дублей runTypeCheck/линт-обёрток (кандидат 3 обзора).
- RunStore — углубление модуля состояния прогона (кандидат 4 обзора, Speculative).
- Унификация сигнатур самих gates (возврат `{ checks, meta }` изнутри gate, а не в паспорте) — отложено: цена ~73 правок вызовов в тестах, выигрыш над текущим решением косметический.
- Авто-discovery этапов по папке (на grilling выбран явный реестр).
- Любые изменения внешнего `--json`-контракта, exit codes, текстов ошибок, состава fingerprint-хэша, поведения `preflight apply`.
- Изменения в SKILL.md/README, кроме одной строки про устройство этапов — по итогам реализации, если потребуется.

## Further Notes

- Источник: архитектурный обзор runner от 2026-08-17 (HTML-отчёт, кандидаты 1+2, оценка Strong). Токен-оптимизации вывода (slim JSON, обрезка detail/fullDiff, хэш без mtime) применены ранее и этой спецификацией не отменяются.
- Критерий приёмки: полный прогон тестов зелёный без правок существующих файлов тестов; новый этап добавляется одним файлом + одной строкой; fingerprint существующих прогонов не инвалидируется.
- Потолок решения: паспорт знает про `xxxMeta` своего gate — если этапов с «богатым» meta станет много, пересмотреть в пользу единой сигнатуры gates (см. Out of Scope).
